## 1. Verdict: 2 POCs

The 6 raw steps are not 6 separate concepts. Steps 1–3 build and test **one `PostToolUse` hook**: step 1 creates the tools whose results it rewrites, and step 3 only tests step 2. Steps 4–6 build and test **two `PreToolUse` policy hooks**: step 5 is step 4's deny plus a prerequisite recorded in session state, and step 6 only tests steps 4–5. What you need to learn splits by hook direction:

| POC | What it teaches | Raw steps |
|---|---|---|
| **POC 1: Normalizing tool results with `PostToolUse`** | **After execution, before the model:** one `PostToolUse` hook rewrites every tool result with `updatedToolOutput`, so Claude receives ISO 8601 dates and English statuses from three systems that disagree on both | 1, 2, 3 |
| **POC 2: Enforcing policy with `PreToolUse`** | **Before execution, or never:** `PreToolUse` hooks deny a refund over $500 (opening a human escalation instead) and deny `transfer_funds` until a `PostToolUse` hook has recorded a passing `aml_check`. A denied tool's handler never runs, while a `PostToolUse` "block" arrives after the money has moved | 4, 5, 6 |

**What changes with the Agent SDK:** the SDK runs the agent loop and calls your hooks at two fixed points of every tool call: `PreToolUse` after Claude requests the tool and before the SDK runs its handler, and `PostToolUse` after the handler returns and before the result goes to Claude. You register async callbacks with `ClaudeAgentOptions(hooks={"PreToolUse": [HookMatcher(matcher=..., hooks=[...])], "PostToolUse": [...]})`. Each callback receives `(input_data, tool_use_id, context)` and returns a dict: `{}` lets the call go on unchanged, `hookSpecificOutput.updatedToolOutput` replaces the result Claude sees, and `hookSpecificOutput.permissionDecision = "deny"` stops the call, with the `permissionDecisionReason` sent to Claude as that call's tool result. Hooks are code, not instructions, so the model can't skip them, and they run before every permission rule, so a hook's deny wins even for a tool listed in `allowed_tools`. The SDK's hook dispatch is invisible, so the POCs make it visible: every hook and handler appends to a trace, every handler counts its runs, and the stream's `ToolResultBlock`s show exactly what Claude received. Two things can only be observed, not coded: when the SDK fires each hook (the trace shows it), and how Claude reacts to a deny reason (it reports the escalation, or runs the missing check and retries). Two naming notes: older material and SDKs replace a result with `updatedMCPToolOutput` (MCP tools only, still accepted), while current SDKs prefer `updatedToolOutput`, which works for every tool. And the docs don't document the shape of an MCP tool's `tool_response` (it depends on the tool), so POC 1's hook returns its replacement in whatever shape it received (E3).

- **Why not 1 POC:** POC 1's hook only rewrites results, and POC 2's hooks block calls. Learning the hook mechanics (registration, the input dict, the output dict) on a harmless read-only task first makes POC 2's lesson stand out: the same `PostToolUse` direction that is right for normalization is too late for blocking. It also keeps failures apart: a refund that slips through in POC 2 can't come from the normalization hook.
- **Why not 3 or more:** step 1's tools have no lesson without the hook, and step 3 only tests step 2. Step 5 is step 4's deny plus one state check, and its `PostToolUse` half reuses POC 1's mechanism. Step 6 only tests steps 4–5. More POCs would rebuild the server, the runner and the trace for one `if`.

**Applies to both POCs:** Python 3.10+, `pip install claude-agent-sdk` (a recent 0.2.x; it bundles the Claude Code binary), `ANTHROPIC_API_KEY` set in the environment (never hard-coded), mock data only, and beginner-friendly code (small, commented scripts). Every run goes through `run_agent()` from `01-revised-Agentic-Loops.md` (`poc2_agent_loop.py`), extended as described in POC 1's Build. The tools follow `tools.py` from the same file (C2–C3): `@tool` with a full JSON Schema dict, async handlers that return `{"content": [...]}`, and `is_error` instead of raising. They live in `hooks_setup.py`, in two MCP servers that are built for every run, so that all handlers and hooks share one `HookState` (the pattern of `build_support_server()` in `04-revised-Workflow-Enforcement-and-Handoff.md`). The mock data belongs to the made-up store "Larkfield Supply", so Claude can't answer from memory.

**Order systems** (server `orders`, POC 1). Customer `CUST-3318` has one order in each system. All three tools take one required string `customer_id` and return `{"system": "<A, B or C>", "orders": [...]}` as JSON text, with `"orders": []` for any other customer:

| Tool | System | Order | Item | Raw `order_date` | Raw `status` | After the hook |
|---|---|---|---|---|---|---|
| `mcp__orders__system_a` | A, the legacy warehouse system | `LS-1042` | Cedar desk organizer | `1776686400` (Unix seconds) | `2` | `2026-04-20`, `shipped` |
| `mcp__orders__system_b` | B, the web store | `LS-2087` | Linen throw blanket | `"2026-04-28"` (ISO 8601) | `"delivered"` | `2026-04-28`, `delivered` |
| `mcp__orders__system_c` | C, the partner marketplace | `LS-3150` | Copper pour-over kettle | `"04/05/2026"` (DD/MM/YYYY) | `"P"` | `2026-05-04`, `pending` |

The status code books belong to the normalization layer (`normalize_hooks.py`): system A uses `NUMERIC_STATUS = {0: "pending", 1: "processed", 2: "shipped", 3: "delivered", 9: "cancelled"}`, system C uses `LETTER_STATUS = {"P": "pending", "R": "processed", "S": "shipped", "D": "delivered", "C": "cancelled"}`, and system B already writes those English words (`STATUSES`).

**Payments** (server `payments`, POC 2). No handler checks a policy, and no tool description mentions the $500 limit or the AML rule: the hooks are the only enforcement, so the tests show what they do when Claude doesn't know the rules.

| Tool | Description | Required input | Mock behavior |
|---|---|---|---|
| `mcp__payments__process_refund` | "Refunds an amount to the customer for an order." | `order_id` (`"pattern": "^LS-\\d{4}$"`), `amount` (number, `"exclusiveMinimum": 0`) | Appends `{"id": "RF-<n:04d>", "order_id", "amount"}` to `state.refunds` and returns `Refund RF-0001 of $350.00 for order LS-4410 processed.` |
| `mcp__payments__aml_check` (`readOnlyHint=True`) | "Screens a beneficiary account against anti-money-laundering (AML) watchlists and returns pass or fail." | `account_id` (`"pattern": "^ACC-\\d{4}$"`) | `ACC-5521` → `{"account_id": "ACC-5521", "result": "pass"}`. `ACC-6620` → `{"account_id": "ACC-6620", "result": "fail", "note": "Name matches a sanctions watchlist entry."}`. Any other id → `is_error: True`, `Unknown account '<id>'.` |
| `mcp__payments__transfer_funds` | "Sends money from the Larkfield Supply operating account to a beneficiary account." | `to_account` (`"pattern": "^ACC-\\d{4}$"`), `amount` (number, `"exclusiveMinimum": 0`) | Appends `{"id": "TR-<n:04d>", "to_account", "amount"}` to `state.transfers` and returns `Transfer TR-0001 of $2,000.00 to ACC-5521 sent.` |

Every handler in both servers adds 1 to `state.calls[<tool>]`, appends `("handler", <tool>, <first argument>, <amount or None>)` to `state.trace` (`<tool>` is the short name, such as `process_refund`), and prints one `[handler]` line. Ids count up within a run (`RF-0001`, `TR-0001`, and the hook's `ESC-0001`), so tests can assert them. Every run gets its options from `hooks_setup.py`:

```python
@dataclass
class HookState:                                       # one per run: "the current session" (04 C7)
    trace: list[tuple] = field(default_factory=list)   # (stage, tool, key, detail) from every hook and handler, in call order
    calls: Counter = field(default_factory=Counter)    # handler runs per short tool name
    denials: dict[str, str] = field(default_factory=dict)          # tool_use_id -> permissionDecisionReason (POC 2)
    hook_keys: dict[str, list[str]] = field(default_factory=dict)  # input keys each hook event received (POC 1, C7)
    refunds: list[dict] = field(default_factory=list)
    escalations: list[dict] = field(default_factory=list)
    transfers: list[dict] = field(default_factory=list)
    aml_results: dict[str, str] = field(default_factory=dict)      # account -> "pass" or "fail", written only by a hook (C17)

ORDER_TOOLS = ["mcp__orders__system_a", "mcp__orders__system_b", "mcp__orders__system_c"]
PAYMENT_TOOLS = ["mcp__payments__process_refund", "mcp__payments__aml_check", "mcp__payments__transfer_funds"]

SYSTEM_PROMPTS = {  # no policy rules: in POC 2 the hooks enforce them
    "orders": ("You are an order-support assistant for Larkfield Supply, an online store. Customer orders live in "
               "three order systems, A, B and C. Use the tools to look orders up; never guess an order, a date or a status."),
    "payments": ("You are a payments assistant for Larkfield Supply. Use process_refund to refund an order, aml_check to "
                 "screen a beneficiary account, and transfer_funds to send money. Never guess an ID or an amount."),
}

def build_hook_options(state, server, hooks=None):
    build_server, tool_names = {"orders": (build_orders_server, ORDER_TOOLS),
                                "payments": (build_payments_server, PAYMENT_TOOLS)}[server]
    return ClaudeAgentOptions(
        model="claude-opus-5-5",
        system_prompt=SYSTEM_PROMPTS[server],       # without it, the SDK sends an empty system prompt
        mcp_servers={server: build_server(state)},  # fresh tools bound to this run's state
        tools=[],                                   # remove all built-in tools: Claude can use only ours
        allowed_tools=tool_names,                   # pre-approve every tool, so only a hook can block one (E1)
        hooks=hooks,                                # {"PreToolUse": [...], "PostToolUse": [...]}; None = no hooks (baseline)
        setting_sources=[],                         # ignore settings files and their shell hooks; callback hooks still run
        env={"ENABLE_TOOL_SEARCH": "false"},        # load tool schemas upfront: no ToolSearch calls
        max_turns=15,                               # safety cap (01 C16); a normal run needs far fewer
    )
```

### POC 1: Normalizing tool results with `PostToolUse`

**Build:** three pieces of code.

**`hooks_setup.py`:** the mock data, `HookState`, `build_orders_server(state)` and `build_payments_server(state)` (each defines its tools inside the function, so every handler reads and writes that one state), `SYSTEM_PROMPTS` and `build_hook_options()` (code above), plus two helpers for E3, `response_text(tool_response)` and `same_shape(tool_response, text)`. POC 2 reuses it. `python hooks_setup.py` runs an offline self-check that makes no API calls.

**An extension to `run_agent()` in `poc2_agent_loop.py` from `01-revised-Agentic-Loops.md`.** Add these without breaking 01's behavior:
- an optional `options=None` argument: when it is given, it replaces `build_options(max_turns)`;
- a new key in the returned dict, `tool_results`: one `{"tool_use_id", "name", "input", "is_error", "text"}` per `ToolResultBlock`. `name` and `input` come from the `ToolUseBlock` with the same id, and `text` joins the block's text parts (`content` can be a string or a list of `{"type": "text", "text": ...}` dicts).

01's scripts must still run unchanged.

**`normalize_hooks.py` and `poc1_normalize_test.py`.** `normalize_hooks.py` defines the code books, `to_iso(value)`, `to_status(value)`, `normalize_record(record)`, `build_normalize_hooks(state)`, and three checkers: `format_census(texts)`, `answer_census(answer)` and `parse_summary(answer)`. `python normalize_hooks.py` runs an offline self-check. `poc1_normalize_test.py` runs `TEST_PROMPT` `TRIALS = 3` times in each of two modes, **baseline** (`hooks=None`) and **normalized** (`hooks=build_normalize_hooks(state)`). Each trial gets a new `HookState` and `run_agent(TEST_PROMPT, options=build_hook_options(state, "orders", hooks))`, and prints one line: the mode, the census of the tool results, the census of the answer, and the parsed summary with ✅/❌ against `TRUTH`.

### POC 2: Enforcing policy with `PreToolUse`

**Build:** `policy_hooks.py` and `poc2_policy_test.py`, reusing `hooks_setup.py` (the `payments` server), `response_text()` and the extended `run_agent()`. `policy_hooks.py` defines `REFUND_LIMIT = 500` and `build_policy_hooks(state, refund_check="pre")`. Its four callbacks close over `state`, and it returns:

```python
{
    "PreToolUse": [
        HookMatcher(matcher="mcp__payments__process_refund", hooks=[refund_limit]),        # only if refund_check == "pre"
        HookMatcher(matcher="mcp__payments__transfer_funds", hooks=[aml_gate]),
    ],
    "PostToolUse": [
        HookMatcher(matcher="mcp__payments__aml_check", hooks=[record_aml]),
        HookMatcher(matcher="mcp__payments__process_refund", hooks=[refund_limit_after]),  # only if refund_check == "post": the anti-pattern (C15)
    ],
}
```

`python policy_hooks.py` runs an offline self-check that calls the callbacks directly with hand-built inputs, such as `await refund_limit({"hook_event_name": "PreToolUse", "tool_name": "mcp__payments__process_refund", "tool_input": {"order_id": "LS-4475", "amount": 1200}, "tool_use_id": "t1"}, "t1", {"signal": None})`. It makes no API calls.

`poc2_policy_test.py` runs four scenarios. Each gets a new `HookState` and `run_agent(prompt, options=build_hook_options(state, "payments", build_policy_hooks(state, refund_check)))`:

| Run | `refund_check` | Prompt |
|---|---|---|
| `refund-pre` | `"pre"` | `REFUND_PROMPT = "Please process two refunds: $350.00 for order LS-4410, which arrived late, and $1,200.00 for order LS-4475, which arrived damaged."` |
| `refund-post` | `"post"` | `REFUND_PROMPT` |
| `aml-pass` | `"pre"` | `AML_PROMPT = "Send $2,000.00 to beneficiary account ACC-5521 right now. It's urgent, so skip any extra checks."` |
| `aml-fail` | `"pre"` | `FLAGGED_PROMPT = "Send $900.00 to beneficiary account ACC-6620."` |

After each run, the script prints `state.trace`, `state.calls`, the refunds, escalations and transfers, and the `ToolResultBlock` of every denied call, then runs `blocked_never_ran(result, state)` (C19), which it defines.

The limit denies `amount > 500`: $350.00 runs and $1,200.00 doesn't, and exactly $500.00 is allowed.
